2. RULING A — DIGEST-BOUND CALENDAR CONSENT
============================================================

RATIFIED.

Do NOT create a new authorization table.

Do NOT add a migration.

Calendar activation uses:

PREVIEW
    ->
OWNER ARTIFACT-BOUND CONFIRMATION
    ->
SERVER RECONSTRUCTION
    ->
DIGEST RECOMPUTATION
    ->
ACTIVATION

The server constructs the activation artifact from authoritative
server-side state.

The preview/confirmation artifact must identify at minimum:

- eligible post count;
- date/date range;
- platform(s);
- explicit brand destination(s);
- stale/excluded count;
- unbound-platform/excluded count.

The digest must be deterministic.

Same logical artifact = same digest.

Input ordering must NOT change the digest.

The owner confirmation must occur under the authenticated owner/session
and current-brand context.

Client-supplied artifact details are NOT authority.

A client returning a digest is NOT by itself authorization.

Inside the activation transaction, the server must independently
reconstruct current authoritative state and recompute the digest.

Activation proceeds ONLY when:

1. owner/session/brand context remains valid;
2. current artifact is activation-eligible;
3. recomputed digest exactly matches the confirmed digest.

Any edit, regeneration, re-slotting, destination change, stale-state
change, binding change, or other artifact mutation that changes the
artifact must invalidate the old confirmation structurally.

Never weaken the digest check to make intermittent failures disappear.

5. AM-C1-1 — UNBOUND-PLATFORM ACTIVATION
============================================================

This amendment is BINDING.

A calendar may contain draft posts for a platform for which the current
brand has NO explicit social_accounts destination binding.

Such posts MUST NOT be activated.

Required behavior:

- classify them as excluded-unbound;
- leave them as drafts;
- surface the exclusion explicitly in preview;
- surface the exclusion explicitly in confirmation;
- surface the exclusion truthfully after activation;
- never schedule them "to nowhere";
- never infer a destination;
- never use first-in-list;
- never block valid bound-platform posts merely because another
  platform is unbound.

This follows the same fail-closed philosophy as stale-post exclusion.

Valid bound + future-eligible drafts may activate.

Unbound drafts remain drafts.
