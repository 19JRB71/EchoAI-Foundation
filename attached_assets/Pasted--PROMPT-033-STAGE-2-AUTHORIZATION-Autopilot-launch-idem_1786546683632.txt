## THE GOVERNING RE-EXECUTION RULE
## (verbatim, into code comment + docs + tests)

"For a persisted launch intent, automatic provider execution is permitted
only when durable evidence proves zero provider side effects across every
prior attempt.

Evidence is CLEAN only when either:

(a) no prior execution attempt exists; or

(b) every prior attempt terminated before any provider call and contains
no partial provider IDs.

Any prior in_progress, interrupted, succeeded,
provider-accepted/manual-review state, or any recorded partial provider
ID makes the intent EVIDENCE-DIRTY and MUST NOT trigger provider execution
automatically."

Companion invariant (Stage-1 A2, unchanged):

For one approved launch intent:

campaign create <= 1
ad-set create <= 1
creative create <= 1
ad create <= 1

A retry may complete a genuinely missing later object only where the design
permits it (it does not — partial chains go to MANUAL_REVIEW); it must
never recreate an earlier successful object.

## SECTION B — BINDING AMENDMENTS
## (D-40; review findings, owner-concurred)


B1. INTERRUPTED ROWS MUST NOT REOPEN EXECUTION

The active-key index guarantees dedup only while a row is:

    in_progress | succeeded

Reconciliation closing an in_progress row as interrupted VACATES the
index.

Therefore, under an index-gated design, a later same-key re-entry could
re-execute against provider objects that may already exist.

Therefore:

RE-EXECUTION IS EVIDENCE-GATED, NOT INDEX-GATED.

Before ANY executeExternal invocation for a persisted intent, the code
consults the durable history for that key, including:

- ledger rows;
- task state;
- partial-chain/provider IDs.

It then applies the governing rule verbatim.

A reconciled interrupted row for the intent is evidence of possible
provider side effects and BLOCKS automatic execution even though the
active-key index no longer covers it.

The index remains the concurrency backstop.

THE INDEX IS NEVER THE SIDE-EFFECT MEMORY.

Do NOT "fix" this by adding interrupted to the index predicate.
That is a schema/index change and therefore a STOP condition.


B2. ALREADY-APPROVED RE-ENTRY BRANCH

TX1 commits before execution.

Therefore the claim guard 409s every ordinary re-approve.

The deliberate re-entry branch is:

If the item is already approved AND has a persisted intent id:

1. Recover the SAME intent id.
2. Recover the SAME idempotency key.
3. Inspect the durable history.
4. Classify that history using the governing evidence-clean/evidence-dirty
   rule.

EVIDENCE-CLEAN:

- no prior execution attempt exists
  (for example, crash between TX1 commit and ledger insert); OR

- every prior attempt terminated before any provider call and has no
  partial provider IDs.

Then:

execution MAY proceed ONCE using the SAME intent/key.

Concurrent evidence-clean re-entries are serialized by the active-key
insert.

Exactly one executes.


EVIDENCE-DIRTY:

Any prior:

- in_progress;
- interrupted;
- succeeded;
- provider-accepted/manual-review state; OR
- recorded partial provider ID

means:

ZERO provider calls.

Return an honest:

    already executed / under review

outcome as appropriate.

No stuck approved-but-never-attempted state may be unreachable.

The evidence-clean branch is precisely the recovery mechanism for the
TX1-committed / execution-never-started crash window.


B3. POST-MANUAL_REVIEW RELAUNCH REMAINS OUT OF SCOPE

Prompt 031 owns owner-mediated retry/reset after launch failure/review.

Prompt 033 MUST NOT invent:

- retry UI;
- relaunch UI;
- reset workflow;
- owner-mediated relaunch behavior.

The honest visible "under review" state is the Prompt-033 boundary.


B4. TASK ATTEMPT SEMANTICS

A stable intent/source id means a later evidence-clean execution attempt
uses an INCREMENTED task attempt number under the existing D-24 G attempt
semantics.

Same source.
New attempt.

Never:

- a new source id;
- a collision;
- a second canonical identity for one intent.

Specify this in the design, enforce it in code, and test it.


B5. campaign_id CONSUMER MINI-INVENTORY

Stage 2 changes:

    autopilot_batch_items.campaign_id

from a POST-SUCCESS value into a PRE-EXECUTION durable intent id.

That means it may be:

- present before a campaigns row exists;
- temporarily dangling during execution;
- indefinitely dangling after a failed/manual-review launch.

Inventory EVERY current reader/join of that column.

For each consumer, classify whether it assumes that a corresponding
campaigns row already exists.

Any consumer that would misinterpret a pre-execution/dangling id must be:

- corrected within the narrow Prompt-033 scope; OR
- STOP AND REPORT if the required correction expands materially beyond
  Prompt 033.

The final report must include the owner-visible wording/state for:

    approved + MANUAL_REVIEW + no campaign row

Nothing silent.

Nothing may imply that a live Facebook campaign exists when it does not.
