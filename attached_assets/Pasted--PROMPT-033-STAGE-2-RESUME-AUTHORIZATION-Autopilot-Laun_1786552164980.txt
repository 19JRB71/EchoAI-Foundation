This corrected D-41 version supersedes all earlier wording.

# SECTION A — D-41 DESIGN RULING

## A1. DURABLE INTENT ID IS DERIVED — NOT STORED

The immutable durable identity already exists:

`autopilot_batch_items.item_id`

For Autopilot Facebook launch only, derive the launch-intent ID deterministically from that immutable item ID.

Conceptually:

`item_id → deterministic intentId → ad_launch:<intentId>`

Required invariant:

**SAME ITEM / SAME INTENT → SAME DERIVED ID → SAME KEY**

across:

* HTTP retry;
* concurrent approval;
* worker retry;
* process restart;
* task retry;
* already-approved re-entry;
* bookkeeping repair;
* reconciliation inspection.

Inverse invariant:

**NEW OWNER-APPROVED ITEM → NEW DERIVED ID → NEW KEY → PERMITTED NEW CHAIN**

Do not store the derived intent ID in `autopilot_batch_items.campaign_id` before execution.

Do not create a new column.

Do not weaken or remove the FK.

---

## A2. DETERMINISTIC-ID IMPLEMENTATION

FIRST inspect the current dependency tree.

### Preferred implementation

If the repository already provides a standards-based UUID v5 helper through its existing dependencies, use that helper.

Use:

* a fixed project-specific namespace UUID;
* immutable `item_id` as the name/input;
* standard RFC UUID v5 semantics.

The namespace UUID becomes load-bearing.

It must be:

* documented;
* fixed;
* test-pinned;
* never generated dynamically.

Using SHA-1 through standards-compliant UUID v5 is acceptable here because the input is an internally generated non-adversarial UUID; this mechanism requires deterministic namespacing, not collision-resistant password hashing.

### If no existing UUID-v5 helper is available

Do NOT add a dependency merely for this prompt.

A small local deterministic UUID derivation is permitted only if all of the following are explicitly specified and regression-locked:

* fixed namespace;
* input bytes;
* hash algorithm;
* UUID byte construction;
* version bits;
* variant bits;
* output formatting.

Do not call a custom SHA-256-derived implementation "UUIDv5."

### Frozen regression vectors are mandatory

Commit fixed test vectors such as:

`known item_id → exact expected intent UUID`

for multiple fixed item IDs.

The test must fail if:

* the namespace changes;
* the derivation algorithm changes;
* byte ordering changes;
* UUID formatting changes.

The derivation function is part of the idempotency contract.

A silent derivation change would retroactively create new keys for existing items and reopen I-32.

# SECTION B — TX1 FINAL SHAPE

The prior D-40 TX1 is superseded.

TX1 now contains **only the claim and already-existing claim-side bookkeeping/budget persistence necessary for approval**.

Conceptually:

`pending item`
→ `TX1 BEGIN`
→ guarded `pending → approved`
→ persist authorized budget/claim data already belonging to that transaction
→ `COMMIT`
→ derive intent ID from immutable `item_id`
→ evaluate evidence gate
→ provider execution OUTSIDE transaction

TX1 MUST NOT persist a pre-execution value into `campaign_id`.

Provider execution happens strictly outside any open claim transaction.

This preserves the original purpose of Design A:

**provider execution can never succeed inside a transaction whose later rollback makes the item appear unclaimed/pending again.**

# SECTION C — `campaign_id` SEMANTICS REMAIN UNCHANGED

`autopilot_batch_items.campaign_id` retains its existing meaning:

**the ID of an actual local campaigns row after launch creation has progressed far enough for that row to exist.**

It is NOT the launch-intent store.

It is NOT written in TX1.

It continues to satisfy its existing FK.

After the campaigns row exists successfully, write the item’s `campaign_id` through the normal post-success/post-creation bookkeeping path.

The final report must identify the exact merged `file:line` where this post-success write occurs.

If the item-level `campaign_id` write fails after provider side effects or campaigns-row creation:

* record the honest persistence/bookkeeping failure;
* route to the existing provider-accepted/manual-review safety behavior as applicable;
* NEVER re-execute the provider merely to repair this field.

D-30.12 remains absolute:

**Bookkeeping failure never causes provider re-execution.**

# SECTION D — CAMPAIGNS-ROW EVIDENCE GATE

D-41 adds a conservative mandatory condition.

Automatic execution is permitted only when:

1. durable attempt history proves zero provider side effects; AND
2. **no `campaigns` row exists for the derived intent ID.**

Before provider execution, inspect the current durable evidence for:

`ad_launch:<derivedIntentId>`

and the corresponding source/task identity.

Evidence sources include, as applicable:

* `external_actions`;
* canonical task state;
* task metadata;
* partial provider IDs;
* `campaigns` row for the derived ID.

## EVIDENCE-CLEAN

Automatic provider execution is permitted only in these cases:

### Clean Case A — no previous attempt

Examples:

* TX1 committed;
* process died before task/ledger/provider execution began.

Conditions:

* no attempt history capable of containing provider effects;
* no partial IDs;
* no campaigns row.

Execution may proceed once using the same derived ID/key.

### Clean Case B — terminal pre-provider failure

A prior attempt may be retried automatically only if durable evidence proves:

* failure occurred before any provider call;
* no partial provider ID exists;
* no campaigns row exists for the intent.

If the failure path created a `launch_failed` campaigns row:

**IT IS NOT EVIDENCE-CLEAN.**

It must not auto-relaunch.

It waits for Prompt 031's future owner-mediated retry/reset semantics.

# SECTION E — EVIDENCE-DIRTY CONDITIONS

Any of the following makes the intent EVIDENCE-DIRTY:

* prior `in_progress` external action;
* reconciled `interrupted`;
* `succeeded`;
* provider-accepted state;
* MANUAL_REVIEW state associated with possible provider execution;
* any recorded Facebook campaign ID;
* any recorded Facebook ad-set ID;
* any recorded Facebook creative ID;
* any recorded Facebook ad ID;
* any partial-chain provider ID in durable task/failure metadata;
* **any `campaigns` row whose primary key is the derived intent ID**.

EVIDENCE-DIRTY means:

**ZERO automatic Facebook provider calls.**

Return an honest visible state such as:

**already executed / under review**

as appropriate.

The active-key unique index remains a concurrency backstop.

It is **not** the side-effect memory.

Do not change the index predicate.

A reconciled `interrupted` row vacating the active-key index does NOT reopen execution.

# SECTION F — ALREADY-APPROVED RE-ENTRY

The claim-first design creates a deliberate re-entry case.

If an item is already:

`approved`

then ordinary pending→approved claim semantics will not win again.

The handler must distinguish:

### Approved + deterministic intent + CLEAN evidence

Re-derive the SAME intent ID from immutable `item_id`.

Evaluate the evidence gate.

If CLEAN:

* use the same intent;
* use the same `ad_launch:<intentId>` key;
* create/increment the appropriate task attempt under D-24 G;
* execute exactly once.

This closes:

**TX1 COMMITTED → PROCESS DIED BEFORE LEDGER INSERT**

without generating a new launch identity.

### Approved + DIRTY evidence

Return an honest already-executed / under-review result.

**ZERO provider calls.**

Do not invent a retry/reset action.

Prompt 031 owns post-review relaunch.
